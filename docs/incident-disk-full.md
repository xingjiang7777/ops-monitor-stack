# 一次磁盘写满故障的复盘

> 场景：本地实验机（8 核 / 16G / 256G SSD，Ubuntu 22.04）跑这套栈的第三周。本文是事后写的复盘，时间与数值为当时的记录。

## 1. 现象

周三晚上 21:40 左右，`ops-nginx` 先挂：访问站点返回 500，`docker logs` 里全是 `No space left on device`。随后 Grafana 也无法写入，页面报 "database or disk is full"。

发现问题的不是我，是 Grafana 打不开才去看的——**当时这套栈还没有配告警规则**，属于典型的"监控装了但没有监控自己"。

## 2. 时间线

| 时间 | 事件 |
| --- | --- |
| 21:32 | 根分区可用空间降到 0，Docker 写日志失败 |
| 21:40 | 打开 Grafana 报错，发现异常 |
| 21:44 | `df -h` 显示 `/` 使用率 100%，`/var/lib/docker` 占 41G |
| 21:52 | 定位到 `ops-nginx` 的 json-file 日志单文件 9.3G |
| 22:05 | `truncate` 日志 + `docker system prune` 释放约 30G |
| 22:20 | 服务恢复，开始补偿配置 |

**从故障发生到发现：8 分钟；从发现到恢复：40 分钟。** 后者才是真正的问题——定位花了 13 分钟，清理和重启花了 27 分钟。

## 3. 根因

直接原因：`/var/lib/docker/containers/<id>/<id>-json.log` 无限增长。

为什么无限增长：

1. compose 里没有为任何服务设置 `logging` 选项，Docker 默认 `json-file` 驱动且**不轮转**；
2. Nginx 的 `access_log` 打在容器 stdout，而 Uptime Kuma 每分钟探测一次，`/healthz` 虽然关了日志，但静态资源的 404 扫描流量不小；
3. 这台机器三个月没做过磁盘巡检。

更深一层：**监控栈本身没有被监控**。node-exporter 一直在采集 `node_filesystem_avail_bytes`，指标是有的，只是没人看，也没有规则去判断"这个斜率会在几小时内吃到 0"。

## 4. 修复动作

事后做了三件事，按优先级：

1. **给所有服务加日志上限**（当天完成）

   ```yaml
   logging:
     driver: json-file
     options:
       max-size: "20m"
       max-file: "3"
   ```

2. **补磁盘预测告警**（当天完成）

   ```promql
   predict_linear(node_filesystem_avail_bytes{fstype!~"tmpfs|overlay|squashfs"}[6h], 4*3600) < 0
   ```

   选 4 小时而不是 1 小时，是因为清理动作需要人来做，1 小时的窗口在半夜等于没告警；选 6 小时的回溯窗口，是为了让斜率不被单次大文件写入带偏。

3. **加一条"使用率 > 85%"的兜底规则**（次日完成）

   预测规则对"突然写入一个巨大文件"不敏感（窗口内样本太少），85% 阈值是补这个盲区。

## 5. 复盘结论

| 问题 | 教训 |
| --- | --- |
| 装监控但没配规则 | 监控的价值在规则，不在看板好看 |
| 只监控业务不监控自己 | 监控组件的宿主机磁盘、容器状态必须一起纳入 |
| 默认配置直接上生产 | Docker 默认日志驱动永不轮转，这是默认值陷阱 |
| 没有巡检习惯 | 阈值告警不能替代定期人工确认 |
